# pi-spec

A spec-driven development workflow extension for the [Pi coding agent](https://pi.dev). It keeps requirements, design, tasks, and verification artifacts in the project, advances through explicit stages, and protects writes according to the current stage.

[中文文档](./README.zh-CN.md)

## Features

- Persists specs under `.pi/specs/<slug>/` with a plugin-managed `state.json`; the frontmatter at the top of each artifact is a read-only view of that state.
- Supports `strict` approval for every planning and verification stage, or `quick` acceptance for requirements/design while retaining human approval before implementation.
- Requires `spec_submit` after an artifact is written; submission validates the document and records its SHA-256 without approving it.
- Offers a no-argument state-aware action menu, Tab completion for `/spec`, and a `spec_request_approval` tool so approving never requires memorizing arguments or typing a subcommand.
- Binds approvals to document hashes and reopens the affected stage when an approved artifact changes or disappears, clearing downstream approvals.
- Protects `state.json` and stage-inappropriate files through the native `tool_call` hook.
- Restores the active spec and tool set after session reload and tree navigation.
- Displays a Workflow-style progress widget in TUI mode and a plain-text status in RPC mode.

## Install

```bash
pi install npm:@maplezzk/pi-spec
```

Then run `/reload` in Pi.

## Commands

Running `/spec` without arguments opens the actions available in the current state, so no argument has to be memorized:

```text
/spec                    Show the actions available right now
/spec new [slug]         Create a spec; prompts for the name and title
/spec use [slug]         Activate a spec; without a name it lists existing specs
/spec status             Show and refresh progress
/spec approve            Confirm the current submitted stage
/spec revise [artifact]  Reopen a stage; without a name it lists reopenable stages
/spec continue           Continue approved implementation tasks
/spec stop               Exit spec mode and restore the previous tools
```

Tab completion lists only the actions that are legal in the current state, and completes existing spec names and reopenable stages. `<artifact>` is one of `requirements`, `design`, `tasks`, or `verification`. The old `--title` flag still works but is no longer needed or documented in the help output.

Most of the time no command is needed at all: the model calls `spec_request_approval` when a document is waiting, which opens the same confirmation dialog as `/spec approve`. Approval still requires your keypress; the tool cannot approve on your behalf, and headless runs are never approved.

## Workflow

```text
strict: requirements → approve → design → approve → tasks → approve → implementation → verification → approve → complete
quick:  requirements → design → tasks → approve → implementation → verification → approve → complete
```

The user must explicitly approve submitted documents in interactive mode. Headless mode never auto-approves. Approving always requires a keypress in a confirmation dialog; `spec_request_approval` only opens that dialog and cannot produce approval by itself. In implementation, the extension tracks `[DONE:TASK-id]` markers in assistant responses and moves to verification after every task in `tasks.md` is complete.

## Write policy

- Planning stages: bash is blocked; only the current artifact may be edited.
- Implementation: source files may be edited, but all `.pi/specs/` artifacts including `tasks.md` are frozen. Use `/spec revise tasks` to change definitions.
- Verification: bash remains available only when it was active before spec mode, and only `verification.md` may be edited.
- `state.json` is always managed by the extension and cannot be written through `write` or `edit`.

## State in documents (frontmatter)

Each artifact starts with a plugin-maintained frontmatter block that states the name, stage, status, approval outcome and task progress, so opening a document shows where the spec stands:

```markdown
---
# Generated by pi-spec for readability; state.json is authoritative for state and approval
spec: checkout-flow
artifact: tasks
title: "Checkout flow"
profile: strict
phase: implementation
status: in_progress
approval: human
approved_at: 2026-09-10T09:12:44.031Z
tasks_done: 2/5
---
```

Rules:

- `state.json` remains the only source of truth. The extension derives the frontmatter from it and overwrites it; the block is never read back. Writing `approval: human` into a document **is not an approval** and never advances a stage.
- Document fingerprints cover only the body after the frontmatter. Synchronizing stage, approval and progress can never invalidate an existing approval, and ticking off a task cannot reopen a stage.
- When the two disagree, `state.json` wins: a legacy spec without the block, or a hand-edited one, is rewritten on activation with a notice naming the affected documents.
- v1 stays readable: for a document without frontmatter the body is the whole file, so its fingerprint matches the legacy record byte for byte, and approvals keep working while the header is added in the current protocol.

## Configuration

There are no runtime settings or configuration switches. `config.example.json` is intentionally empty. Use the `/spec` commands and project artifacts instead.

### Recovery and tool ownership

Session/tree navigation selects a spec; it does not roll back its shared on-disk state. Recovery checks the state shape, approval chain and document fingerprints. Missing or corrupt targets block tools until `/spec use <slug>` succeeds or `/spec stop` exits. Legacy v1 records without `completedTasks` and legacy documents without frontmatter remain readable; malformed progress is rejected.

`spec_submit` is exposed only while drafting, and `spec_request_approval` only while a document is awaiting approval. Tool restoration preserves observable additions/removals by other extensions and excludes unregistered tools. Pi exposes the final active set, not ownership of each change: if another extension disables a tool already hidden by spec, that intent is unobservable and stopping spec can restore that tool. Coordinate overlapping restrictions explicitly; this is not a sandbox.

Argument completion has no access to a session context, so it uses the project directory observed from the most recent session or command event. Completion therefore reflects the directory of the current session, not an arbitrary one.

## Stage procedures and migration

The package ships bilingual `procedures/*.json` catalogs for requirements, design, tasks, implementation and verification. Before each model request the `context` hook supplies exactly one current procedure and one short current-state message, removing only spec-owned stale messages. It reuses matching content or restores missing content after compaction; it does not append full procedures to session history. Inactive mode removes spec context, awaiting approval supplies only wait/revise instructions, and complete supplies a completion notice without a new artifact. Missing, invalid or unreadable procedure resources block tools with an explicit error; repair the package and `/spec use <slug>` to retry.

`/skill:spec-mode` is removed. Only `configure-pi-spec` remains globally discoverable as an operations entrypoint; stage methods load automatically. Remove any separately copied legacy spec-mode skill to avoid contradictory instructions. Procedures follow the shared Pi extension locale.

Progress now comes only from persisted `completedTasks` plus new DONE markers from the current execution run, not historical conversation text. Revising requirements/design/tasks clears affected progress. DONE is not evidence of successful testing; verification must record actual outcomes and unrun checks. Waiting documents cannot be edited until revised. Tool restrictions do not sandbox bash or arbitrary custom tools.
